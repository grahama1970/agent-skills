### Core Philosophy: Beyond Linting to Semantic Correctness

Fixing violations isn't just about making a linter (like `pylint`, `flake8`) happy. It's about enforcing **semantic correctness** and **architectural integrity**. A violation often signals a deeper design flaw that can lead to technical debt, bugs, and an unmaintainable codebase. The goal is to shift from a reactive ("the CI failed") to a proactive ("this pattern prevents future errors") mindset.

### 1. Architectural Pattern Violations

These are high-level violations that break the intended structure and flow of the application.

#### a) Violation: Tight Coupling & Poor Separation of Concerns
*   **What it is:** Components (modules, classes, functions) know too much about each other's internal workings. Changing one module forces changes in many others.
*   **Common Pitfall:** Directly instantiating dependencies inside a class or function, leading to a web of hard-coded imports.
    ```python
    # VIOLATION: ServiceA is tightly coupled to the concrete implementation ServiceB.
    class ServiceA:
        def __init__(self):
            self.service_b = ServiceB()  # Direct instantiation

        def operation(self):
            return self.service_b.do_something()
    ```
*   **State-of-the-Art Fix: Dependency Injection (DI) & Inversion of Control (IoC)**
    *   **Principle:** Dependencies are "injected" into a class from the outside, often by a framework or container. This adheres to the **Dependency Inversion Principle (D)** from SOLID.
    *   **Approach:** Use interfaces (Abstract Base Classes - `abc.ABC`) to define contracts. Depend on abstractions, not concretions.
    *   **Tools/Frameworks:** While Python doesn't have a built-in DI container like Java's Spring, modern libraries like **`dependency-injector`** or **FastAPI's built-in DI system** are excellent. You can also implement a simple form manually.
    ```python
    # FIXED: Using ABC and Constructor Injection.
    from abc import ABC, abstractmethod

    class ServiceBInterface(ABC):
        @abstractmethod
        def do_something(self): ...

    class ServiceB(ServiceBInterface):
        def do_something(self):
            return "Result from B"

    class ServiceA:
        def __init__(self, service_b: ServiceBInterface):  # Depend on abstraction
            self.service_b = service_b  # Injected dependency

        def operation(self):
            return self.service_b.do_something()

    # Composition Root: Assemble the object graph at the application's entry point.
    service_b = ServiceB()
    service_a = ServiceA(service_b)
    ```

#### b) Violation: God Object / Large Class
*   **What it is:** A single class that knows or does too much, violating the **Single Responsibility Principle (S)**.
*   **Common Pitfall:** A class named `Utils`, `Helpers`, or `Processor` that accumulates unrelated methods over time, becoming a dumping ground for functionality.
*   **State-of-the-Art Fix: Composition over Inheritance & Domain-Driven Design (DDD)**
    *   **Principle:** Break down the monolith into smaller, cohesive classes each with a single, well-defined reason to change.
    *   **Approach:**
        1.  **Identify Bounded Contexts:** What are the distinct domains in your application? (e.g., `UserManagement`, `OrderProcessing`, `ReportGeneration`).
        2.  **Refactor by Extracting Classes:** Move related methods into new, focused classes.
        3.  **Use Composition:** The original class (if it still needs to orchestrate these actions) should hold *instances* of these new classes rather than their logic.
    ```python
    # VIOLATION: A God class handling users, emails, and data processing.
    class ApplicationManager:
        def create_user(self, username): ...
        def delete_user(self, user_id): ...
        def send_welcome_email(self, user): ... # Email logic doesn't belong here
        def generate_user_report(self): ...      # Reporting logic doesn't belong here

    # FIXED: Composition with distinct services.
    class UserService:
        def create_user(self, username): ...
        def delete_user(self, user_id): ...

    class EmailService:
        def send_welcome_email(self, user): ...

    class ReportService:
        def generate_user_report(self, users): ...

    # The main application now composes these services.
    class Application:
        def __init__(self, user_svc, email_svc, report_svc):
            self.user_svc = user_svc
            self.email_svc = email_svc
            self.report_svc = report_svc
    ```

### 2. Common Code & Design Pitfalls

These are more granular but widespread issues that affect code quality and reliability.

#### a) Violation: Improper Exception Handling
*   **What it is:** Catching overly broad exceptions (`except:`) or using exceptions for control flow (which is slow and misleading).
*   **Pitfall:**
    ```python
    try:
        price = float(user_input)
    except:  # Catches KeyboardInterrupt, SystemExit, everything! Never do this.
        price = 0
    ```
*   **State-of-the-Art Fix: Defensive Programming & Precise Exception Handling**
    *   **Principle:** Be explicit about the exceptions you can handle. Let others propagate to be handled at a higher level.
    *   **Approach:**
        1.  Catch specific exceptions (`except ValueError:`).
        2.  Use context managers for resources (files, locks, sockets) to ensure clean-up.
        3.  Consider the "Result Pattern" (from functional programming) as an alternative to exceptions for expected failures. Libraries like **`result`** or writing your own `Result[T, E]` class can make error states explicit in the type system.
    ```python
    # FIXED: Specific exception handling and a context manager.
    try:
        with open('data.json', 'r') as f:  # File will be closed even if an error occurs
            data = json.load(f)
    except FileNotFoundError:
        logging.warning("Config file not found, using defaults.")
        data = {}
    except json.JSONDecodeError as e:
        # Handle malformed JSON specifically
        raise ConfigurationError("Invalid JSON config") from e
    ```

#### b) Violation: Primitive Obsession
*   **What it is:** Using basic data types (strings, integers, dicts, lists) to represent domain concepts, leading to validation logic scattered across the codebase.
*   **Pitfall:** Representing an email address as a `str` and validating its format in every function that uses it.
*   **State-of-the-Art Fix: Value Objects / Data Classes**
    *   **Principle:** Create small, immutable objects that represent concepts in your domain. They encapsulate validation and behavior.
    *   **Approach:** Use Python's **`dataclasses`** (or `pydantic.BaseModel`) to easily create these objects. Validation happens at the point of creation.
    ```python
    # FIXED: Using a Value Object with Pydantic (highly recommended for data validation).
    from pydantic import BaseModel, EmailStr, validator

    class Customer(BaseModel):
        name: str
        email: EmailStr  # Pydantic's built-in type handles validation
        age: int

        @validator('age')
        def check_age(cls, v):
            if v < 0:
                raise ValueError('Age must be positive')
            return v

    # Usage: Validation is centralized and automatic.
    try:
        customer = Customer(name="Alice", email="alice@example.com", age=30)
        # customer.email is guaranteed to be a valid format.
    except ValidationError as e:
        print("Invalid customer data:", e)
    ```

#### c) Violation: Inconsistent State & Poor Encapsulation
*   **What it is:** Class internals are exposed and can be modified directly from outside, potentially creating invalid or inconsistent states.
*   **Pitfall:** Using public attributes instead of properties or getter/setter methods.
    ```python
    class BankAccount:
        def __init__(self, balance):
            self.balance = balance  # Public attribute? Anyone can set it to -100!

    account.balance = -100 # Violation
    ```
*   **State-of-the-Art Fix: Properties & Immutability**
    *   **Principle:** Use `@property` to control access to attributes. Make objects immutable (`frozen=True` in dataclasses) where possible to avoid state changes altogether.
    *   **Approach:**
        ```python
        from dataclasses import dataclass

        @dataclass(frozen=True)  # Immutable state -> thread-safe and predictable
        class BankAccount:
            _balance: int

            @property
            def balance(self) -> int:
                return self._balance

            def deposit(self, amount: int) -> 'BankAccount':
                if amount <= 0:
                    raise ValueError("Amount must be positive.")
                # Return a new instance instead of modifying state.
                return BankAccount(self._balance + amount)
        ```

### 3. State-of-the-Art Tooling & Enforcement

You cannot fix violations you cannot see. Automation is key.

1.  **Static Analysis & Linting:**
    *   **`flake8`** with plugins (`flake8-bugbear`, `flake8-bandit`): Finds style guide violations, common bugs, and security issues.
    *   **`pylint`:** More opinionated and comprehensive, checks for code smells and design issues.
    *   **`mypy`** or **`pyright`:** **Essential.** Static type checkers that catch type-related errors before runtime, enforcing contracts and improving readability and tooling (autocomplete).

2.  **Automated Formatting:**
    *   **`black`:** The uncompromising code formatter. Eliminates all debates about code style. Just run `black` and it's done.
    *   **`isort`:** Automatically sorts and formats imports.

3.  **Pre-commit Hooks:**
    *   Use **`pre-commit`** framework to run all the above tools automatically before every `git commit`. This prevents violations from ever entering the repository.

4.  **CI/CD Integration:**
    *   All these checks **must** run in your Continuous Integration pipeline (e.g., GitHub Actions, GitLab CI). The build should fail if any critical violations are found, ensuring main branch integrity.

### Summary: The High-Reasoning Workflow

1.  **Detect:** Use `pre-commit` hooks and CI with `flake8`, `mypy`, and `pylint`.
2.  **Categorize:** Is the violation stylistic (fix with `black`), a potential bug (fix logic), or architectural (requires refactoring)?
3.  **Refactor:** Apply the appropriate pattern: Dependency Injection for coupling, Value Objects for primitives, Composition for God objects.
4.  **Prevent:** Enforce the new patterns through code reviews, architectural decision records (ADRs), and by making the correct way to code also the easiest way.

By treating "violations" as opportunities to improve the system's design rather than just style errors, you build a more robust, maintainable, and scalable Python project.
