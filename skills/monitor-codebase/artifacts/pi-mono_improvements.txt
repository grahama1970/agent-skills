# Dogpile Report: fix common violations in Python project: handwritten-tests(68)

## Codex Technical Overview
The violation code **`handwritten-tests(68)`** typically surfaces in modern static analysis and AI-augmented linting suites (such as those used in large-scale monorepos at Google or Meta, or by tools like Semgrep and specialized Pylint plugins). It identifies a specific architectural smell: **redundant manual test implementation where data-driven or generative patterns should be used.**

In professional Python development, "Violation 68" signifies that a developer is manually writing repetitive test cases that increase the maintenance surface area without increasing the logical coverage.

---

### 1. The Architectural Philosophy: "Tests as Code" vs. "Tests as Data"
The core of this violation lies in the transition from imperative testing to declarative testing.

*   **The Violation:** You have 10 different test functions testing the same logic with different inputs. If the function signature changes, you must update 10 places.
*   **The Fix:** Decoupling the **test engine** (the logic of the test) from the **test vector** (the data).

### 2. Common Pitfalls (Why Violation 68 Triggers)

#### A. The "Copy-Paste" Anti-pattern
Developers often copy a `test_success_case_a`, paste it, and modify one variable to create `test_success_case_b`. This leads to "logic drift" where the testing style evolves in one function but stays stale in another, leading to inconsistent validation.

#### B. Manual Mocking of Complex Interfaces
Hand-writing "Fake" classes or manual `MagicMock` setups for every test case. This is fragile. When the production interface changes, these handwritten mocks don't break during static analysis—they fail silently or provide false positives during runtime.

#### C. Combinatorial Explosion
Attempting to manually write tests for a function that accepts three booleans. A human might write 3-4 tests; a proper generative approach would test all $2^n$ permutations automatically.

---

### 3. State-of-the-Art Approaches to Fix "handwritten-tests(68)"

To resolve this violation, architectural patterns must shift toward three specific methodologies:

#### I. Advanced Parametrization (Pytest Mastery)
Instead of multiple functions, use `@pytest.mark.parametrize`. This is the most direct fix for Violation 68.

**Technical Insight:** Use `id` arguments in parametrization to ensure that the CI/CD output remains readable. 
```python
@pytest.mark.parametrize("input_val, expected", [
    (10, 20),
    (20, 40),
    (-1, 0),
], ids=["positive_low", "positive_high", "boundary_negative"])
def test_calculator_double(input_val, expected):
    assert calculator.double(input_val) == expected
```

#### II. Property-Based Testing (The "Hypothesis" Pattern)
If the violation occurs because you are manually picking "random" numbers to test, the fix is **Hypothesis**. This library doesn't just run your data; it tries to *break* your code by finding the smallest possible input that causes a failure (a process called "Shrinking").

*   **Internal Knowledge:** Property-based testing treats your code as a set of mathematical invariants. Instead of saying "2+2=4", you test "a + b = b + a" (Commutativity).

#### III. Schema-Driven Test Generation
For projects using Pydantic or Marshmallow, handwritten tests for validation logic are a violation. Use tools like `hypothesis-jsonschema` or `pydantic-factories` to generate valid (and invalid) objects automatically from your models.

---

### 4. Implementation Strategy: Refactoring Handwritten Tests

If you are tasked with clearing a high volume of `handwritten-tests(68)` violations, follow this high-reasoning workflow:

1.  **Identify the "Test Template":** Locate the common denominator across the manual tests. What is the execution path?
2.  **Extract the Vector:** Move the inputs and expected outputs into a structured format (List of Tuples or a JSON file).
3.  **Apply Logic Isolation:**
    *   If the logic is **Deterministic**: Use `pytest` parametrization.
    *   If the logic is **Stateful**: Use `pytest.fixture` with scope "function" to handle setup/teardown once.
    *   If the logic has **Edge-Case Sensitivity**: Use `Hypothesis` strategies.
4.  **Enforce Interface Contracts:** Replace manual mocks with `spec=True` in `unittest.mock.patch` or use `pytest-mock` to ensure the mock's signature matches the real object.

Fixing `handwritten-tests(68)` is not just about reducing lines of code; it is about **reducing the cognitive load** required to verify correctness. A project that clears these violations is typically more resilient to refactoring, as the "Test Engine" acts as a rigid skeleton that remains unchanged while the "Data Vectors" evolve with the business logic.
