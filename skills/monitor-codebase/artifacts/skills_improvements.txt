### 1. Core Problem Definition: What Does "handwritten-tests" Violation Mean?

The violation indicates that the project relies on manually written, ad-hoc test scripts (e.g., `test_manual.py`, `check.py`) instead of using a **dedicated, structured testing framework** like `pytest` or `unittest`.

These handwritten tests are characterized by:
*   **Lack of Framework Features:** No built-in test discovery, setup/teardown fixtures, assertion rewriting, or parallel execution.
*   **Brittleness:** Tests often contain hardcoded paths, credentials, and data, making them non-portable and fragile.
*   **Poor Reporting:** They use `print` statements for output, requiring manual inspection to determine pass/fail status.
*   **No Isolation:** Tests are rarely isolated from each other, leading to cascading failures where one test's side-effects break another.
*   **High Maintenance:** Any change to the system's API requires a painful, manual update of every affected test script.

The number `(51)` is likely the specific rule ID from the linter (e.g., WPS351 in `wemake-python-styleguide`).

### 2. Architectural Patterns and the Role of Testing

Testing isn't an afterthought; it's an integral part of the system's architecture. The choice of testing strategy directly influences and is influenced by the application's design.

**a) Testability as an Architectural Goal:**
A system is "testable" if its components can be isolated and validated in isolation. This is achieved through patterns that promote **low coupling** and **high cohesion**.
*   **Dependency Injection (DI):** This is the cornerstone of testability. Instead of hardcoding dependencies (e.g., `import database`), a class or function receives them as parameters. This allows you to inject mock or fake objects during testing.
    *   **Violation:** A handwritten test cannot easily mock a database connection because the code under test creates it internally.
    *   **Solution:** Refactor code to accept the `database` connection as an `__init__` parameter. The test can then inject a `FakeDatabase` object.

**b) The Onion/Clean Architecture:**
This architecture enforces testability by separating concerns into layers (Entities, Use Cases, Interface Adapters, Frameworks & Drivers). The inner layers have no dependencies on outer layers. This allows you to test the core business logic (Use Cases and Entities) without any external systems like web frameworks or databases, leading to incredibly fast and reliable unit tests.

**c) Hexagonal Architecture (Ports & Adapters):**
Similar to Onion, it defines "ports" (interfaces) that the core application uses, and "adapters" that implement these interfaces for specific technologies (e.g., a SQL repository adapter, a REST API adapter). For testing, you can create "in-memory" adapters (e.g., an in-memory repository using a list) to test the core application logic without the slow and complex real infrastructure.

**The key insight:** Handwritten tests are almost always a symptom of an architecture that wasn't designed with testability in mind. Fixing the tests *forces* you to fix the architecture.

### 3. Common Pitfalls of Handwritten Tests

1.  **False Positives/Negatives:** The most dangerous pitfall. A test might `print("OK")` even when the code is broken, or fail because of an unrelated environmental issue, eroding trust in the test suite.
2.  **No Test Isolation:** Tests share global state. Test A creates a file `output.txt`, Test B reads it, assumes specific content, and fails if Test A didn't run or run in a different order. This makes tests non-deterministic.
3.  **Integration Hell:** They often test everything at once—reading from a real database, calling a live API, and writing to the filesystem. This makes tests slow, flaky, and difficult to debug. Is the bug in the logic, the network, or the database?
4.  **Missing Edge Cases:** Without a framework encouraging parameterized tests, it's tedious to test multiple inputs. Handwritten tests usually only check the "happy path."
5.  **Lack of Tooling Integration:** They cannot be easily integrated with CI/CD pipelines, test coverage tools (`coverage.py`), or IDE test runners, which are essential for modern development workflows.

---

### 4. State-of-the-Art Approach: The Testing Pyramid & Modern Toolchain

The goal is to replace the monolithic, handwritten script with a stratified, automated testing strategy.

**a) The Testing Pyramid:**
*   **Unit Tests (Base of Pyramid - Many):** Fast, isolated tests for individual functions, classes, or modules. Use **pytest** as the framework of choice for its simplicity and power.
    *   **Techniques:** Extensive use of **pytest fixtures** for setup/teardown and **monkeypatch** or **unittest.mock** to isolate code.
*   **Integration Tests (Middle - Fewer):** Test the interaction between multiple components (e.g., a service and a database). Use a real database in a known state, often provided by test containers or library-specific testing tools (e.g., `pytest-django`).
*   **End-to-End (E2E) Tests (Top - Few):** Test the entire system from the user's perspective (e.g., using Selenium or Playwright for web apps). These are the slowest and most brittle tests.

**b) Modern Toolchain:**
*   **Framework: `pytest`.** The industry standard. Offers fixtures, parameterization, and a powerful plugin ecosystem.
*   **Test Doubles: `unittest.mock`.** Built-in to Python, perfect for creating stubs, mocks, and fakes to isolate units of code.
*   **Coverage: `coverage.py`.** Measures which lines of code are executed by the tests. Aim for high coverage, but prioritize testing critical logic over chasing 100%.
*   **CI/CD: GitHub Actions, GitLab CI, Jenkins.** Automatically run the entire test suite on every pull request and push to the main branch. This is non-negotiable.
*   **Advanced Techniques:**
    *   **Property-Based Testing (`hypothesis`):** Instead of testing example inputs, you define rules ("properties") your code must always satisfy, and the framework generates countless edge cases to test it.
    *   **Snapshot Testing (`syrupy` or `pytest-snapshot`):** Useful for testing the output of serializers, UI components, or configuration generators. It saves a "golden" output and alerts you on any change.

### 5. Actionable Migration Plan

Fixing 51 violations is a significant refactoring effort. Do it incrementally.

1.  **Step 0: Install the Toolchain.**
    ```bash
    pip install pytest coverage hypothesis
    ```

2.  **Step 1: Analyze and Prioritize.**
    *   Identify the most critical business logic covered by the handwritten tests. This is your highest priority.
    *   Identify code that is inherently untestable (e.g., highly coupled modules).

3.  **Step 2: Refactor for Testability (The Prerequisite).**
    *   **Break down monolithic scripts** into smaller functions and classes with single responsibilities.
    *   **Introduce Dependency Injection.** Pass file handles, database connections, and API clients as arguments instead of creating them inside functions.
    *   This is the most challenging but most important step. It improves the production code itself.

4.  **Step 3: Write a Single Unit Test with `pytest`.**
    *   Pick one small, pure function from your refactored code.
    *   Create a `tests/` directory and a `test_*.py` file.
    *   Write a test using `pytest`'s assert statements.
    *   Run it with `pytest -xvs path/to/test_file.py`.

5.  **Step 4: Create Fixtures for Common Setup.**
    *   Replace any repeated setup code in your handwritten tests (e.g., creating test data) with `pytest` fixtures.

6.  **Step 5: Incrementally Replace and Delete.**
    *   For each scenario covered by a handwritten test, write a corresponding `pytest` test.
    *   Once the new test passes and provides equivalent (or better) coverage, **delete the code from the handwritten test script.**
    *   **Crucially:** Use your CI/CD pipeline to ensure the new test suite is run automatically. The handwritten script should eventually become empty and can be deleted.

7.  **Step 6: Measure and Improve.**
    *   Run `coverage run -m pytest` and then `coverage report` to identify untested code.
    *   Gradually expand your test coverage, moving from unit tests to integration tests as needed.

It requires a shift in mindset from "testing as a separate task" to "testing as an integral part of the design process." By adopting a modern testing pyramid, leveraging tools like `pytest`, and—most importantly—refactoring the application for testability using patterns like Dependency Injection, you transform a brittle, unmaintainable project into a robust, scalable, and confident codebase.
