# Input: Defensive technique document with fields: control_id, name, description, parent_id, mind

You are a cybersecurity analyst generating grounded QRA (Question-Reasoning-Answer) pairs for exactly one MITRE D3FEND defensive technique.

Your task:
Generate grounded QRA pairs that help practitioners understand:
- what the technique is,
- how D3FEND describes it,
- where it fits in the D3FEND taxonomy,
- and, only if explicitly present in the source, how it is implemented or what scope it applies to.

You must use only the admissible source fields provided in the prompt.

GROUNDING RULES:
1. Every factual claim in every answer must be supported by admissible source text.
2. A claim is valid only if it is either:
   - a verbatim restatement of source text, or
   - a conservative paraphrase that preserves the same actors, actions, scope, and modality.
3. Never add examples, implications, best practices, causal claims, attack mappings, or explanatory context that is not explicitly present in the admissible source.
4. PRESERVE MODALITY exactly.
   - If the source says "can help", the answer must also express possibility, not certainty.
   - Do not strengthen, generalize, or overstate source language.
5. If no admissible source text supports a grounded pair, return zero pairs.

SOURCE ADMISSIBILITY:
You may use only these fields:
- name: official technique name
- description: technique definition and explanation
- parent_id: parent category in D3FEND taxonomy
- mind: top-level D3FEND tactic

NOT ADMISSIBLE:
- external URLs or links
- page navigation elements
- version/date metadata
- inferred ATT&CK relationships unless explicitly stated in description
- license text
- any background knowledge not present in the admissible fields

If a provided field contains both admissible and inadmissible material, use only the admissible text span.

PAIR_TYPE RULES:
Use only these pair_types for D3FEND techniques:
- defense_description
- implementation_guidance
- taxonomy_context
- scope_clarification

Definitions:
- defense_description:
  What the technique is and how the description defines or characterizes it.
  Definition and mechanism are one aspect. Do not split them into separate pairs.

- implementation_guidance:
  Use only if the description explicitly states actions, steps, or operational practices.
  Do not infer implementation advice from a definition alone.

- taxonomy_context:
  Where the technique fits in the D3FEND hierarchy, using only parent_id and/or mind.

- scope_clarification:
  Use only if the description explicitly states applicability, target objects, boundaries, or protected scope.
  Do not infer operating context or protection claims.

DISTINCTNESS RULES:
1. Each pair must cover a different aspect.
2. Generate at most one pair per pair_type.
3. Prefer fewer pairs over weak pairs.
4. Do not create a pair just to fill an available pair_type slot.

SOURCE PRECEDENCE:
1. description
2. name
3. parent_id and mind

If a higher-priority field is missing or weak, use fewer pairs. Do not invent content.

INSUFFICIENCY RULES:
Return zero pairs only if none of the admissible fields support any grounded pair.

Additional guidance:
- A missing or minimal description blocks defense_description, implementation_guidance, and scope_clarification.
- taxonomy_context may still be generated if parent_id or mind is present.
- If no admissible verbatim evidence can support any pair, return zero pairs.

OUTPUT REQUIREMENTS:
Return exactly one top-level JSON object.
The only top-level keys allowed are:
- pairs
- skipped_reason

If pairs are generated:
- skipped_reason must be null

If zero pairs are generated:
- pairs must be []
- skipped_reason must explain which insufficiency rule prevented generation

JSON SCHEMA:
{{
  "pairs": [
    {{
      "question": "string",
      "reasoning": "string",
      "answer": "string",
      "pair_type": "defense_description | implementation_guidance | taxonomy_context | scope_clarification",
      "control_id": "string",
      "evidence_quotes": [
        {{
          "quote": "string",
          "relevance": "string"
        }}
      ],
      "confidence": "high | medium",
      "actionable_for": "implementation | audit | risk_assessment | training"
    }}
  ],
  "skipped_reason": "string or null"
}}

FIELD CONSTRAINTS:
- question:
  Must explicitly contain both the exact control ID and the exact technique name.

- reasoning:
  Reason about the subject matter. State why the answer follows for THIS
  defensive technique specifically: the mechanism, condition, or consequence that makes it
  true.
  Be precise, concise, and comprehensive. Precise: no hedging or filler.
  Concise: no words that carry nothing. Comprehensive: nothing load-bearing
  omitted.
  There is no minimum and no maximum length. Satisfying all three may take six
  words or six paragraphs; let the defensive technique decide, and stop when the reasoning
  is complete. Never pad to look thorough, and never truncate a real
  explanation to look tight.
  Do NOT explain provenance, grounding, validity, or which field you read.
  evidence_quotes already carries that.
  Never restate the defensive technique description verbatim.
  The reasoning must be specific enough that it could not be copied onto a
  different defensive technique. If it would read identically for another entry, it is wrong.

- answer:
  1-4 sentences, maximum 150 words.
  Include only grounded content from admissible fields.

- evidence_quotes:
  Must contain verbatim text from admissible fields only.
  Each quote must be 1-150 words.
  Every factual proposition in the answer must be traceable to at least one evidence_quote.
  One evidence_quote may support multiple propositions if it explicitly contains them.

- confidence:
  "high" = answer stays very close to verbatim source wording
  "medium" = answer is a conservative paraphrase of verbatim source wording
  Do not use "low"

HARD CONSTRAINTS:
1. Maximum 4 pairs.
2. Maximum 1 pair per pair_type.
3. Every question must explicitly contain both the control_id and the technique name.
4. Every answer must have at least one evidence_quote from an admissible field.
5. If source support is insufficient, do not generate the pair.
