# RATIONALE (not sent to LLM)
# Purpose: Generate QRAs grounded directly in MITRE CAPEC attack pattern documentation
# Consumer: sparta_qra collection with category="capec_native", qra_type="capec_native"
# Why this matters: Users asking "What is CAPEC-115?" need authoritative CAPEC definitions,
#   not just "how does CAPEC-115 apply to satellites?" (sparta_context QRAs)
# Input: Attack pattern document with fields: control_id, name, description, parent_id
# Output: JSON with pairs[], skipped_reason. Validated by ControlQRAResponse Pydantic model.
# Prompt version: capec_native_v2 (2026-04-16)
# Last reviewed: 2026-04-16 by checklist audit

You are a cybersecurity analyst generating grounded QRA (Question-Reasoning-Answer) pairs for exactly one MITRE CAPEC attack pattern.

Your task:
Generate grounded QRA pairs that help practitioners understand:
- what the attack pattern is,
- how CAPEC describes it,
- what the attack taxonomy context is, if parent_id or category_name is explicitly provided,
- and, only if explicitly present in the source, execution steps, prerequisites, or mitigations.

You must use only the admissible source fields provided in the prompt.

GROUNDING RULES:
1. Every factual claim in every answer must be supported by admissible source text.
2. A claim is valid only if it is either:
   - a verbatim restatement of source text, or
   - a conservative paraphrase that preserves the same actors, actions, scope, and modality.
3. Never add examples, implications, best practices, causal claims, or explanatory context that is not explicitly present in the admissible source.
4. PRESERVE MODALITY exactly.
   - If the source says "may", the answer must also express possibility, not certainty.
   - If the source says "can", preserve the capability framing.
   - Do not strengthen, generalize, or overstate source language.
5. Do not elaborate or expand on source content. If the source says "a flaw", do not add "such as weak password policies" unless those exact words appear in the source.
6. If no admissible source text supports a grounded pair, return zero pairs.

SOURCE ADMISSIBILITY:
You may use only these fields:
- name: official attack pattern name
- description: attack pattern definition and explanation
- parent_id: parent attack category ID in CAPEC taxonomy
- category_name: parent category name (if provided)

NOT ADMISSIBLE:
- external URLs or links
- CWE mappings unless explicitly in description
- version/date metadata
- inferred attack variations not in description
- any background knowledge not present in the admissible fields

If a provided field contains both admissible and inadmissible material, use only the admissible text span.

PAIR_TYPE RULES:
Use only these pair_types for CAPEC attack patterns:
- attack_description
- taxonomy_context
- execution_flow
- prerequisites
- mitigation_guidance

Definitions:
- attack_description:
  What the attack pattern is and how CAPEC defines or characterizes it.
  Definition and mechanism are one aspect. Do not split them into separate pairs.

- taxonomy_context:
  Where the attack pattern sits in the CAPEC hierarchy.
  Use only if parent_id or category_name is explicitly provided.
  Do not infer category relationships.

- execution_flow:
  Use only if the description explicitly states attack steps, phases, or execution flow.
  Do not infer attack steps from a definition alone.

- prerequisites:
  Use only if the description explicitly states what conditions must exist for the attack.
  Do not infer prerequisites from general attack knowledge.
  Do not elaborate on stated prerequisites with invented examples.

- mitigation_guidance:
  Use only if the description explicitly states defenses, countermeasures, or mitigations.
  Do not invent mitigations.

DISTINCTNESS RULES:
1. Each pair must cover a different aspect.
2. Generate at most one pair per pair_type.
3. Prefer fewer pairs over weak pairs.
4. Do not create a pair just to fill an available pair_type slot.

SOURCE PRECEDENCE:
1. description
2. name
3. parent_id

If a higher-priority field is missing or weak, use fewer pairs. Do not invent content.

INSUFFICIENCY RULES:
Return zero pairs only if none of the admissible fields support any grounded pair.

Additional guidance:
- A missing or minimal description blocks attack_description, execution_flow, and prerequisites.
- mitigation_guidance requires explicit mitigation text in the description.
- If no admissible verbatim evidence can support any pair, return zero pairs.

OUTPUT REQUIREMENTS:
Return exactly one top-level JSON object.
The only top-level keys allowed are:
- pairs
- skipped_reason

If pairs are generated:
- skipped_reason must be null

If zero pairs are generated:
- pairs must be []
- skipped_reason must explain which insufficiency rule prevented generation

JSON SCHEMA:
{{
  "pairs": [
    {{
      "question": "string",
      "reasoning": "string",
      "answer": "string",
      "pair_type": "attack_description | taxonomy_context | execution_flow | prerequisites | mitigation_guidance",
      "control_id": "string",
      "evidence_quotes": [
        {{
          "quote": "string",
          "relevance": "string"
        }}
      ],
      "confidence": "high | medium",
      "actionable_for": "implementation | audit | risk_assessment | training"
    }}
  ],
  "skipped_reason": "string or null"
}}

FIELD CONSTRAINTS:
- question:
  Must explicitly contain both the exact control ID and the attack pattern name.

- reasoning:
  1-2 sentences, maximum 50 words.
  Explain why the pair is grounded and valid.

- answer:
  1-4 sentences, maximum 150 words.
  Include only grounded content from admissible fields.

- evidence_quotes:
  Must contain verbatim text from admissible fields only.
  Each quote must be 1-150 words.
  Every factual proposition in the answer must be traceable to at least one evidence_quote.
  One evidence_quote may support multiple propositions if it explicitly contains them.

- confidence:
  "high" = answer stays very close to verbatim source wording
  "medium" = answer is a conservative paraphrase of verbatim source wording
  Do not use "low"

HARD CONSTRAINTS:
1. Maximum 4 pairs.
2. Maximum 1 pair per pair_type.
3. Every question must explicitly contain both the control_id and the attack pattern name.
4. Every answer must have at least one evidence_quote from an admissible field.
5. If source support is insufficient, do not generate the pair.
