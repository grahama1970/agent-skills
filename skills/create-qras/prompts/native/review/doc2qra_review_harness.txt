TEST CASE 1: Authoritative Technical Document
================================================================================

INPUTS:
  title: "NIST SP 800-53 Rev 5 - AC-17 Remote Access"
  url: "https://nvd.nist.gov/800-53/Rev5/control/AC-17"
  content: |
    AC-17 REMOTE ACCESS
    Control: a. Establish and document usage restrictions, configuration/connection
    requirements, and implementation guidance for each type of remote access allowed; and
    b. Authorize each type of remote access to the system prior to allowing such connections.

    Discussion: Remote access is access to organizational systems (or processes acting on
    behalf of users) that communicate through external networks such as the Internet.
    Types of remote access include dial-up, broadband, and wireless.

EXPECTED BEHAVIOR:
  - Generate 2-3 pairs
  - source_quality: "authoritative"
  - definition: YES - "Remote access is access to organizational systems..."
  - requirement: YES - "shall establish and document" / "shall authorize"
  - scope: MAYBE - if "external networks such as the Internet" is explicit enough

VALIDATION:
  [ ] source_quality = "authoritative" (NIST official documentation)
  [ ] Modality preserved exactly from "shall" statements
  [ ] evidence_quotes are verbatim from the control text
  [ ] No background knowledge about NIST added

TEST CASE 4: Technical Reference with Threats
================================================================================

INPUTS:
  title: "CWE-79: Improper Neutralization of Input During Web Page Generation"
  url: "https://cwe.mitre.org/data/definitions/79.html"
  content: |
    CWE-79: Improper Neutralization of Input During Web Page Generation ('Cross-site Scripting')

    Description: The product does not neutralize or incorrectly neutralizes user-controllable
    input before it is placed in output that is used as a web page that is served to other users.

    Extended Description: Cross-site scripting (XSS) vulnerabilities occur when an application
    includes untrusted data in a new web page without proper validation or escaping.

    Consequences: Technical Impact: Execute Unauthorized Code or Commands; Read Application Data;
    Modify Application Data

    Potential Mitigations: Use a vetted library or framework that does not allow this weakness
    to occur. When generating output, encode/escape it appropriately for the context.

EXPECTED BEHAVIOR:
  - Generate 3-4 pairs
  - source_quality: "authoritative"
  - definition: YES - CWE-79 definition
  - threat_description: YES - consequences/impact
  - mitigation: YES - "use a vetted library", "encode/escape"

VALIDATION:
  [ ] source_quality = "authoritative" (CWE official source)
  [ ] Question includes "CWE-79" identifier
  [ ] Consequences preserved as described, not embellished
  [ ] Mitigations are verbatim from source

================================================================================
VALIDATION CHECKLIST (apply to all outputs)
================================================================================

SOURCE QUALITY:
[ ] source_quality field present and accurate
[ ] Authoritative → extract with confidence
[ ] Non-authoritative → prefer zero pairs

GROUNDING:
[ ] Every factual claim traces to evidence_quote
[ ] Evidence_quotes are verbatim from source document
[ ] No background knowledge about frameworks/standards added
[ ] No inferences about "what the document probably means"

MODALITY:
[ ] "shall" -> mandatory preserved
[ ] "should" -> recommendation preserved
[ ] "must" -> mandatory preserved
[ ] "may" -> permissive preserved
[ ] No strengthening or weakening

PAIR_TYPE RULES:
[ ] definition used only when source explicitly defines
[ ] requirement used only when source states obligation
[ ] threat_description used only when source describes threat
[ ] mitigation used only when source states countermeasure
[ ] relationship used only when source explicitly relates concepts
[ ] scope used only when source states applicability

DISTINCTNESS:
[ ] Each pair covers genuinely different aspect
[ ] Same sentence not split into multiple pair_types
[ ] Consolidate repeated concepts into one pair

RELEVANCE:
[ ] Only cybersecurity-relevant content extracted
[ ] No author biographical information (age, education, credentials)
[ ] No publication metadata (impact factor, citations, h-index)
[ ] No website boilerplate or navigation
[ ] No general IT content unrelated to security

INSUFFICIENCY:
[ ] <50 words substantive content → zero pairs
[ ] Boilerplate/navigation only → zero pairs
[ ] Forum/Q&A discussion → zero pairs or very few
[ ] No cybersecurity content → zero pairs
[ ] Cannot ground claims → zero pairs

FORMAT:
[ ] Valid JSON
[ ] Only "items" and "source_quality" at top level
[ ] All required fields present in each pair
[ ] confidence is "high" or "medium" only

================================================================================
BEHAVIORAL EXPECTATIONS (v3 specific)
================================================================================

Non-negotiable rule:
  If the same sentence contains both a definition and a requirement,
  generate only one pair (choose the dominant aspect).

Source quality awareness:
  Non-authoritative sources (forums, Q&A, user comments) should result in
  zero pairs or at most 1-2 pairs with medium confidence.

Reference vs. content:
  "See NIST SP 800-53 for details" is a reference, not content.
  Do not generate pairs from references - only from actual content.
