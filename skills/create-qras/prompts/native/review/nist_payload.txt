You are a cybersecurity analyst generating grounded QRA (Question-Reasoning-Answer) pairs for exactly one NIST SP 800-53 security control.

Your task:
Generate grounded QRA pairs that help practitioners understand:
- what the control requires,
- how NIST describes it,
- what control family it belongs to, if that family information is explicitly provided,
- and, only if explicitly present in the source, what review, oversight, or scope requirements the control contains.

You must use only the admissible source fields provided in the prompt.

GROUNDING RULES:
1. Every factual claim in every answer must be supported by admissible source text.
2. A claim is valid only if it is either:
   - a verbatim restatement of source text, or
   - a conservative paraphrase that preserves the same actors, actions, scope, requirement strength, and modality.
3. Never add examples, implications, best practices, tool recommendations, causal claims, or explanatory context that is not explicitly present in the admissible source.
4. PRESERVE REQUIREMENT STRENGTH exactly.
   - If the source uses imperative requirement language such as "Define," "Assign," "Require," "Review," or "Establish," the answer must preserve that requirement strength.
   - Do not recast required actions as optional guidance.
   - If the source says "should," preserve recommendation rather than requirement.
   - If the source says "shall," preserve the mandatory modality.
5. PRESERVE BRACKETED PLACEHOLDERS exactly.
   - If the source contains bracketed placeholders such as "[Assignment: organization-defined time period]", do not resolve, simplify, replace, or invent values for them.
   - If an answer references a placeholder, reproduce it exactly as written in the source.
6. If no admissible source text supports a grounded pair, return zero pairs.

SOURCE ADMISSIBILITY:
You may use only these fields:
- control_id: official control identifier
- name: official control name
- description: control definition and requirements
- family_id: control family identifier, if provided
- family_name: control family name, if provided
- parent_control_id: parent control identifier for enhancements, if provided

NOT ADMISSIBLE:
- external URLs or links
- inferred implementation details not in the source
- generic security advice
- version/date metadata
- family names inferred from abbreviations if not explicitly provided
- any background knowledge not present in the admissible fields

If a provided field contains both admissible and inadmissible material, use only the admissible text span.

PAIR_TYPE RULES:
Use only these pair_types for NIST controls:
- control_description
- family_context
- review_or_oversight_requirement
- scope_clarification

Definitions:
- control_description:
  What the control requires and how NIST defines it.
  Definition, obligations, and main mechanism are one aspect. Do not split them into multiple pairs.

- family_context:
  Where the control sits in the NIST control family structure.
  Use only if family_id, family_name, or parent_control_id is explicitly provided.
  Do not infer family names from abbreviations.

- review_or_oversight_requirement:
  Use only if the source explicitly states review, approval, monitoring, notification, alignment, or other oversight-related requirements.
  Do not invent assessment procedures or compliance tests.

- scope_clarification:
  Use only if the source explicitly states applicability, target accounts, target systems, boundaries, or scope conditions.
  Do not infer scope from general control context.

DISTINCTNESS RULES:
1. Each pair must cover a different aspect.
2. Generate at most one pair per pair_type.
3. Prefer fewer pairs over weak pairs.
4. Do not create a pair just to fill an available pair_type slot.
5. Do not restate the same obligation in multiple pair_types.

SOURCE PRECEDENCE:
1. description
2. name
3. family_id / family_name / parent_control_id

If higher-priority fields are missing or weak, use fewer pairs. Do not invent content.

INSUFFICIENCY RULES:
Return zero pairs only if none of the admissible fields support any grounded pair.

Additional guidance:
- A missing or minimal description blocks control_description, review_or_oversight_requirement, and scope_clarification.
- family_context may still be generated if family_id, family_name, or parent_control_id is present.
- If no admissible verbatim evidence can support any pair, return zero pairs.

Return exactly one top-level JSON object.

- pairs

- question:
  Must explicitly contain both the exact control ID and the exact control name.

- reasoning:
  1-2 sentences, maximum 50 words.
  Explain why the pair is grounded and valid.

- answer:
