You are a cybersecurity analyst generating grounded QRA (Question-Reasoning-Answer) pairs for exactly one MITRE CWE weakness entry.

Your task:
Generate grounded QRA pairs that help practitioners understand:
- what the weakness is,
- how CWE describes it,
- what the weakness taxonomy context is, if parent_id or category_name is explicitly provided,
- and, only if explicitly present in the source, detection methods, mitigations, or consequences.

You must use only the admissible source fields provided in the prompt.

GROUNDING RULES:
1. Every factual claim in every answer must be supported by admissible source text.
2. A claim is valid only if it is either:
   - a verbatim restatement of source text, or
   - a conservative paraphrase that preserves the same actors, actions, scope, and modality.
3. Never add examples, implications, best practices, causal claims, or explanatory context that is not explicitly present in the admissible source.
4. PRESERVE MODALITY exactly.
   - If the source says "may lead to", the answer must also express possibility, not certainty.
   - If the source says "can allow", preserve the capability framing.
   - Do not strengthen, generalize, or overstate source language.
5. If no admissible source text supports a grounded pair, return zero pairs.

SOURCE ADMISSIBILITY:
You may use only these fields:
- name: official weakness name
- description: weakness definition and explanation
- parent_id: parent weakness category ID in CWE taxonomy
- category_name: parent category name (if provided)

NOT ADMISSIBLE:
- external URLs or links
- CVE examples unless explicitly in description
- CAPEC mappings unless explicitly in description
- version/date metadata
- any background knowledge not present in the admissible fields

If a provided field contains both admissible and inadmissible material, use only the admissible text span.

PAIR_TYPE RULES:
Use only these pair_types for CWE weaknesses:
- weakness_description
- taxonomy_context
- detection_methods
- consequence_description
- mitigation_guidance

Definitions:
- weakness_description:
  What the weakness is and how CWE defines or characterizes it.
  Definition and mechanism are one aspect. Do not split them into separate pairs.

- taxonomy_context:
  Where the weakness sits in the CWE hierarchy.
  Use only if parent_id or category_name is explicitly provided.
  Do not infer category relationships.

- detection_methods:
  Use only if the description explicitly states how to detect or identify the weakness.
  Do not infer detection methods from general security knowledge.

- consequence_description:
  Use only if the description explicitly states what happens when the weakness is exploited.
  Do not infer consequences.

- mitigation_guidance:
  Use only if the description explicitly states fixes, countermeasures, or mitigations.
  Do not invent mitigations.

DISTINCTNESS RULES:
1. Each pair must cover a different aspect.
2. Generate at most one pair per pair_type.
3. Prefer fewer pairs over weak pairs.
4. Do not create a pair just to fill an available pair_type slot.

SOURCE PRECEDENCE:
1. description
2. name
3. parent_id

If a higher-priority field is missing or weak, use fewer pairs. Do not invent content.

INSUFFICIENCY RULES:
Return zero pairs only if none of the admissible fields support any grounded pair.

Additional guidance:
- A missing or minimal description blocks weakness_description, detection_methods, and consequence_description.
- mitigation_guidance requires explicit mitigation text in the description.
- If no admissible verbatim evidence can support any pair, return zero pairs.

OUTPUT REQUIREMENTS:
Return exactly one top-level JSON object.
The only top-level keys allowed are:
- pairs
- skipped_reason

If pairs are generated:
- skipped_reason must be null

If zero pairs are generated:
- pairs must be []
- skipped_reason must explain which insufficiency rule prevented generation

JSON SCHEMA:
{
  "pairs": [
    {
      "question": "string",
      "reasoning": "string",
      "answer": "string",
      "pair_type": "weakness_description | taxonomy_context | detection_methods | consequence_description | mitigation_guidance",
      "control_id": "string",
      "evidence_quotes": [
        {
          "quote": "string",
          "relevance": "string"
        }
      ],
      "confidence": "high | medium",
      "actionable_for": "implementation | audit | risk_assessment | training"
    }
  ],
  "skipped_reason": "string or null"
}

FIELD CONSTRAINTS:
- question:
  Must explicitly contain both the exact control ID and the weakness name.

- reasoning:
  1-2 sentences, maximum 50 words.
  Explain why the pair is grounded and valid.

- answer:
  1-4 sentences, maximum 150 words.
  Include only grounded content from admissible fields.

- evidence_quotes:
  Must contain verbatim text from admissible source fields only.
  Each quote must be 1-150 words.
  Every factual proposition in the answer must be traceable to at least one evidence_quote.
  One evidence_quote may support multiple propositions only if it explicitly contains them.

- confidence:
  "high" = answer stays very close to verbatim source wording
  "medium" = answer is a conservative paraphrase of verbatim source wording
  Do not use "low"

HARD CONSTRAINTS:
1. Maximum 4 pairs.
2. Maximum 1 pair per pair_type.
3. Every question must explicitly contain both the control_id and the weakness name.
4. Every answer must have at least one evidence_quote from an admissible field.
5. If source support is insufficient, do not generate the pair.
