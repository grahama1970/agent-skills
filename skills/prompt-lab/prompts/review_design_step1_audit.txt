# Design Audit Request — Code-First Review

## CRITICAL: Ground Every Finding

You MUST only report findings about elements that are VISIBLE in the screenshots or PRESENT in the source code. Do NOT:
- Hallucinate UI elements, components, or features that don't exist
- Reference generic dark-theme patterns from your training data
- Invent component names — use the names from the source code and visible UI labels
- Report "scrollbar", "command palette", "file sidebar" unless you can SEE them

## Review Priority Order

1. **Source Code** (PRIMARY) — The TSX/component code tells you what the application IS, what data it displays, what interactions it supports. Read the code to understand the component architecture.
2. **Screenshots** (CONFIRMATION) — Visual evidence of what the code produces. Verify that what the code describes matches what you see.
3. **Design Tokens** (REFERENCE) — Optional specification. If empty, skip token-based analysis entirely.

## Your Task (Step 1: Audit)

### Phase A: DESCRIBE What You See (MANDATORY)

For EACH screenshot, write a short description:
- Screenshot filename
- What view/tab is shown (read the tab label or heading)
- What data is displayed (tables, cards, charts, badges, counts)
- What interactive elements are visible (buttons, search inputs, filters, tabs)
- What state the UI is in (loaded, empty, filtered, selected)

### Phase B: Analyze the Source Code

If source code is provided, identify:
- Component names and their responsibility
- Data hooks and what collections they query
- Interactive patterns (click handlers, search, filter, sort, pagination)
- Layout structure (grid, flex, sidebar+main, tabs)

### Phase C: Identify Findings

Compare what the code intends vs what the screenshots show. For each finding:
1. **Severity**: high (breaks usability for the persona's workflow), medium (noticeable gap), low (polish)
2. **Category**: data-display, interaction, layout, typography, color, spacing, accessibility
3. **Element**: The exact component name from the source code AND what it looks like in the screenshot
4. **Issue**: What's wrong — grounded in what you SEE and what the code DOES
5. **Current**: What you observe
6. **Recommended**: Specific fix
