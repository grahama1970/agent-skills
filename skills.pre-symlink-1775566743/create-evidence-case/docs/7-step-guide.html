/create-evidence-case — 7-Step Agent Flow

CAE (Claims-Arguments-Evidence) tree builder. The agent orchestrates existing skills, reasons about results, and makes all judgment calls. Python is a thin data collector.
6 deterministic gates. 3 possible verdicts. No magic floats.

CORE PRINCIPLE

Entities from different sentence components must resolve to the same SPARTA technique. If they don't, the question spans unrelated domains → verdict is INCONCLUSIVE.

Sentence Decomposition
AGENT — native LM capability, no tool needed

Parse the question into Given (context/constraints) and Then (search targets/threats) components. Each component becomes a separate query.

Input

The raw question text.

"Given the F-36's use of third-party FPGA vendors, which SPARTA supply chain attack vectors should we prioritize in our CMMC Level 3 compliance audits?"
Given (context/constraints):
  - F-36                        → project context
  - third-party FPGA vendors    → SPARTA controls term

Then (search targets/threats):
  - SPARTA supply chain attack vectors  → SPARTA controls term
  - CMMC Level 3 compliance audits      → framework mapping term
Output → Step 2

A DecompositionNode with given_components[], then_components[], and component_queries{}.

decomposition feeds per-component recall queries
Per-Component QRA Retrieval
SKILL — /memory recall (run in PARALLEL, one per component)

For EACH component from Step 1, query /memory recall scoped to sparta_qra.

Command (per component) 
.claude/skills/memory/run.sh recall \
  --q "<component text>" \
  --collections sparta_qra \
  --k 10
Output

QRA items with fields: control_id, tactical_tags, question, answer, scores{bm25, graph, dense}.

Gate 1: Recall

At least 1 QRA returned across all components.

0 QRAs → early exit as INCONCLUSIVE — "Needs /dogpile Tier 3 research."

Early exit if no QRAs: Persist as INCONCLUSIVE grade C, score 0.25. Skip remaining gates.
QRA items + component results flow to entity extraction

Gate 2b: Grounding

grounding_ok == true AND fabricated_count == 0

Any fabricated IDs → blocks SATISFIED verdict. Actionable typos → early exit INCONCLUSIVE/NOT_SATISFIED with /memory clarify.

Early exit if actionable typos: Call /memory clarify, persist with clarification suggestions, skip remaining gates.
grounded entities + QRAs feed the technique bridge check
Same-Technique Check
AGENT — CRITICAL JUDGMENT

The core question: Do entities from different components resolve to the SAME technique?

What to check
  1. tactical_tags across components — do they cluster into 1-2 techniques?
  2. related_pairs from /extract-entities — do cross-component edges exist?
  3. Explicit controls in question text — do they share a tactic?

Bridge criteria (any one sufficient):

Bridge TypeCondition
Shared tacticExplicit controls share the same tactic (e.g., both "Harden")
Related pairsCross-component entity edges from /extract-entities
Tag coherenceDominant tag covers ≥50% of QRAs, ≤3-5 scattered techniques
Broad grounded>5 techniques BUT entities are grounded AND ≥3 QRAs
Gate 3: Technique Bridge

At least one bridge type confirmed.

No shared technique → entities exist but span unrelated domains.

Early exit if no bridge: Call /memory clarify → persist as INCONCLUSIVE grade C. Clarify explains the gaps.
If bridge found → Semantic Relation Check

When ≥2 explicit controls in the question, run a deterministic grounded relevance check. Verifies the controls are semantically related enough to produce a coherent answer.

Gate 4: Semantic Relation

Controls are answerable together.

Controls exist but aren't related → INCONCLUSIVE with /memory clarify.

Sub-claim decomposition

If multiple technique groups exist, build meaningful sub-claims from evidence. Single technique → no decomposition needed.

Gate 4c: Decompose

Always passes — informational only.

technique bridge + sub-claims feed formal verification
Clarification
SKILL — /memory clarify (called on failures in Steps 3-4)

Clarification is not always a separate step — it's called inline when earlier gates fail. Produces structured disambiguation.

Command 
.claude/skills/memory/run.sh clarify \
  --q "<question>"
Output

Related entities, unrelated entities, suggested decompositions, and clarifying questions. Used to confirm or revise the same-technique assessment.

When called:

  • Step 3: actionable typo warnings → clarify suggests corrections
  • Step 4: no technique bridge → clarify explains domain gaps
  • Step 4: semantic relation fails → clarify suggests rephrasing
  • Step 6: plausibility fails → clarify suggests SPARTA-native terms
all gates + evidence feed formal verification

Gate 5b: Plausibility (conditional)

Only fires when grounding passed BUT not_in_corpus warnings exist. Catches questions that use real IDs in nonsensical contexts (e.g., "CM0028 quantum encryption").

Not plausible → call /memory clarify, suggest SPARTA-native terms.

all 6 gates determine the verdict
Final Verdict + Report
AGENT — synthesize all results

Verdict = f(gates_passed, total_gates)

VerdictConditionMeaning
SATISFIED All 6 gates pass Components resolve, technique bridge confirmed, proof strengthens
INCONCLUSIVE 2-5 gates pass Some covered, others need research. OR no shared technique. T2 LLM may override.
NOT_SATISFIED 0-1 gates pass Off-topic, no entities, or fabricated premises

Graph Model (CAE Tree)

ClaimNode (root — question + verdict)
  ├── DecompositionNode (Given/Then structure)
  ├── StrategyNode (verification approach — "agent_driven")
  │   └── EvidenceNode[] (QRA or skill result, OSCAL method: TEST|EXAMINE|COMPUTE)
  └── VerdictNode (state + grade + score + reasoning)

What You Must NOT Do

  • Do NOT regex-parse control IDs — read structured fields from recall results
  • Do NOT use stopword lists — you understand language, use that
  • Do NOT auto-pass verdicts — if evidence coherence is unclear, say INCONCLUSIVE
  • Do NOT skip the same-technique check — this IS the core criterion
  • Do NOT assume one QRA matches the full question — decompose per component
  • Do NOT use /memory recall without --collections sparta_qra

Worked Example: SATISFIED

"What SPARTA countermeasures protect F-36 flight software from firmware tampering during avionics maintenance windows?"

2. Recall"firmware tampering" → 4 QRAs (CM0028), "maintenance windows" → 3 QRAs (SV-MA)
