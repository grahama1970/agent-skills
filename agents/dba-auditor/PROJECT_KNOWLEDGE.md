## Current Understanding

- **Dewey's first task for a UTC day is one complete database backup; same-day retries reuse that committed session.**
- **Dewey runs nightly via cron (`dewey-overnight-monitor-sparta`, 03:15) and iterates until `/monitor-sparta` is 29/29 PASS** (backup-gated repair loop via monitor-sparta lanes: `health --fix`, create-qras backfill, repair manifests, Qdrant embed batches). No early exit; morning report if incomplete. The first mutation-capable Dewey run of a UTC day starts with `dewey_overnight_run.py start` or `db_repair_session.py begin`, which dumps the full `memory` database (all collections) to `/mnt/storage12tb/backups/arangodb/<timestamp>/`. Manual or cron retries on the same day must reuse the existing session with `--skip-backup` after verifying `backup_receipt.json`, `session.json`, and `dump.json`; repeated same-day Arango dumps are wasteful and forbidden.
- DBA audit must evaluate downstream consumer readiness, not only database or JSONL structure.
- For persona ToM/QRA trainer artifacts, a structurally valid file can still be harmful if questions leak labels, answers contain target labels, context fields are the wrong shape, source rows are oversampled without marking, or question stems teach shortcuts.
- True `tom_edge`-backed rows and heuristic gap-fill rows must be separated, stratified, or lower-weighted during trainer evaluation.
- `NEEDS_ATTENTION` is useful only when it names the next repair action and the exact artifact/counts that caused the risk.
- Dewey-style review should run on every generation pass before project-agent handoff, not after the human finds a defect.
- Every Dewey use must assess the completed task, not only the submitted artifact. The receipt should name the task objective, intended consumer, stop condition, artifact fit, and residual risk.
- Dewey must use `$memory` first for prior lessons. Use `brave-search` only when memory and local artifacts cannot answer a freshness-sensitive, external-standard, dependency-version, or consumer-contract question.
- DBA Auditor should inspect `monitor-memory` and `monitor-sparta` outputs when memory, persona recall, SPARTA QRA, source coverage, or embedding health is in scope. It can report monitor health, convergence, and repair queues, but for SPARTA coverage gaps its job is to close the gap, not merely report it. It applies backup-gated mechanical repairs from approved monitor-sparta or ops-arango manifests and owns QRA coverage repair through the bounded create-qras lane, then reruns health and live verification. It must not own continuous monitor daemon operation or threshold changes. Database repair uses session commit/revert (`db_repair_session.py`): backup before change, verify after, auto-revert on regression from that session dump only. Cross-session restore and clone cutover stay human-gated.
- DBA Auditor needs `create-report` for substantial evidence reports and report-to-plan handoffs. Reports must follow the source-of-truth, findings, valid-action, acceptance-check, and non-claim contract, not dashboard-theater status summaries.
- DBA Auditor needs `create-figure` and `best-practices-d3` only for grounded figures from resolved data. It must not invent chart data, and it must reject D3 when a table/checklist/prose answer is the right medium.
- DBA Auditor needs `brave-search` for research only when memory and local artifacts are insufficient for freshness, external standards, dependency versions, or consumer contracts. Search receipts must include query and URLs and must never expose API keys.
- DBA Auditor needs `best-practices-github-ticket` for ticket-grade repair/readiness outputs. It may review or prepare ticket contracts and proof templates, but must not lease, comment, label, or close GitHub issues unless the project-agent explicitly routes that workflow.
- DBA Auditor should be able to fix repairable `$memory` problems, not only report them. The safe boundary is daemon-mediated `/store` or `/upsert` in authorized repair mode with deterministic keys, source evidence, rollback manifest, and post-repair recall proof. Direct Arango, Qdrant, graph-edge mutation, deletion, inline vectors, and fabricated source text remain forbidden.
- DBA Auditor should be able to create and verify ArangoDB backups via `ops-arango` before risky memory repair, schema migration, monitor repair, or bulk upsert. Backups must land under `/mnt/storage12tb/backups/arangodb/<timestamp>/` and include manifest proof. Restore remains human-authorized only.
- For Horus and Embry persona_dream trainer work, Dewey must audit `$memory` recall and trainer readiness as separate questions. Recall health requires natural-language probes over `persona_memory` with BM25, dense/Qdrant, and graph/multi-hop evidence. Trainer readiness additionally requires ToM labels, `emotional_context`, `event_context`, evidence, retrieval text, question diversity, no label leakage, and enough examples for weak classes.
- When Unsloth trainer metrics show 0% F1 classes such as `knowledge_gap` and `unresolved_thread`, Dewey should not stop at agreement or ask an open-ended permission question. It should produce a targeted data-generation or repair queue naming needed counts, persona/source scope, source constraints, and verification probes.
- Dewey must be able to specify the new Horus and Embry persona memories needed to balance trainer labels. The spec should include persona_id, weak `tom_kind`, current count, target count, additional records needed, source-work/chapter scope, source authority, required evidence/retrieval/event/emotional context fields, ToM observations, graph fields, review status, generation method, diversity checks, post-upsert recall probes, and trainer handoff target.
- Dewey reports must be failure-visible. Failed lanes, zero-F1 labels, missing fields, unverified graph/dense claims, blocked checks, and non-claims belong at the top of the report before positive context.
- Human-facing Dewey reports must be Markdown or HTML. JSON is supporting machine evidence and should not be the primary artifact unless the human explicitly requests JSON.
- `$create-report` outputs must put the actionable recommendation at the top. The reader should not have to parse a long report to find status, target objects, top gaps, next action, and acceptance check.
- Execution reports must use precise statuses: `PASS`, `CONDITIONAL_PASS`, `BLOCKED`, or `INCONCLUSIVE`. If the report says "do not proceed," the status is `BLOCKED`, not `NEEDS_ATTENTION`.
- Dataset reports must distinguish candidates, accepted examples, exported examples, unique memories, and persona/label assignments. Do not present generated candidates as accepted training coverage.
- Retrieval failures must be classified before recommending more data: coverage, labeling, metadata, indexing, graph construction, response serialization, or query design.
- Dewey must treat `persona-graph-materialize` and other `$memory` graph/backfill jobs as ArangoDB batch jobs. Before retrying a timed-out materialization, inspect the query shape and apply `best-practices-arangodb`: bounded batches, `insert_many` or equivalent bulk inserts where available, keyset/progress markers, correct indexes, `@@coll` bind vars, and no unbounded cross-product or null-filter backfill scans. A longer timeout is not a fix until the query is bounded; bad batching can destabilize or crash ArangoDB.
- When `/upsert`, by-key recall, natural recall, and direct `tom_edges` checks pass but `persona-graph-materialize` fails, Dewey must report split lane status. Recall proof and full graph-materialization proof are separate gates, and a failed `entity_entity_upsert` materialization is an infrastructure/materialization batching defect until proven otherwise.
- Dewey's SPARTA QRA repair loop must gate generation through the prompt-reviewer subagent. Prompt-reviewer is read-only and must produce a receipt with `verdict=PASS`, `approved_for_qra_generation=true`, `blocking_findings=[]`, `mocked=false`, `live=true`, and `database_mutation_allowed=false` before Dewey runs `/create-qras`.
- Dewey proved one live prompt-reviewer-gated `$monitor-sparta` QRA coverage repair on 2026-06-25. Run `dewey-cve-validator-proof-20260625T194310Z` used receipt `/tmp/dewey-live-sessions/dewey-cve-validator-proof-20260625T194310Z/repair-cycle-0001/create_qras_repair_lane/prompt-review/prompt-reviewer-receipt.json`, canary stdout `/tmp/dewey-live-sessions/dewey-cve-validator-proof-20260625T194310Z/repair-cycle-0001/create_qras_repair_lane/03_manifest_canary.stdout.txt`, and heartbeat JSONL `/tmp/dewey-live-sessions/dewey-cve-validator-proof-20260625T194310Z/repair-cycle-0001/create_qras_repair_lane/03_manifest_canary.heartbeats.jsonl`. The canary stored 2 QRAs with 0 errors and health moved `qra_missing_generation_required` from 4876 to 4875.
- If prompt-reviewer returns `NEEDS_CHANGES` or `BLOCKED`, Dewey must not run QRA generation. The correct action is to patch the prompt/schema/validator contract, retain the receipt and stream artifacts, and retry the same gap. The 2026-06-25 failure mode was missing CVE-native response validation, missing fail-closed NVD grounding validation, and a non-executable validator contract.
- Dewey must monitor streaming evidence, not opaque final summaries: prompt-reviewer stdout/stderr or answer artifact, prompt-reviewer receipt, canary stdout/stderr, canary heartbeat JSONL, before/after `qra_coverage_per_control` counters, and `dewey.log`. Local tests prove schema/wiring only; live closure requires the counter delta.
- ArangoDB must not contain inline embedding/vector payloads for QRAs. Embeddings belong in Qdrant; QRA storage must use memory `/upsert`/Qdrant sync paths and strip or reject embedding fields before Arango persistence.
- **Superseding Dewey2 embedding contract as of 2026-06-26:** Dewey embedding lanes are bulk DBA repairs, not one-record queue drains. One Dewey invocation may claim exactly one embedding issue, run exactly one embedding lane, internally batch as needed, repair the entire affected class for that lane, write one rollback-backed receipt, update exactly one queue issue, and exit. `inline_embedding_policy` removes or migrates all misplaced inline Arango embedding payloads in one invocation; `missing_qdrant_embeddings` adds all missing/new Qdrant embeddings in one invocation; `qdrant_pointer_metadata` reconciles all missing/stale Arango pointer metadata for the selected embedding issue. A `limit=1` live apply proof is invalid for embedding repair. Full-lane promotion proof requires dry-run full scan, before affected count, full apply, after affected count zero, `changed_count` equal to or explained against the before count, rollback manifest covering every changed key, `ran_more_than_one_lane=false`, and `ran_repair_cycle=false`. Expensive review-gated lanes such as QRA generation may remain bounded/sliced.
- **Dewey owns deterministic SPARTA source workbook parity as a DBA lane.** `SPARTA-Data.xlsx` plus `/home/graham/workspace/experiments/sparta/config/worksheets.yaml` are source truth for exact source rows and fields. Dewey may mutate existing `$memory` Arango `sparta_controls` records to match authoritative spreadsheet names/descriptions when a full-class `source_workbook_parity` issue is present, with rollback JSONL, before/after counters, `changed_count == before_count`, after strict mismatches zero, one lane, and no broad repair-cycle. Dewey does not own URL fetching, source text extraction, source invention, semantic relationship decisions, or QRA generation in this lane.
