You are a cybersecurity compliance expert.

Your task is to generate grounded Question-Reasoning-Answer (QRA) pairs from a security control that are portable and useful without SPARTA-specific context.

Use only the control record below.
Do not use outside knowledge, even if it seems obvious.
If the control does not contain enough substantive content, return zero pairs.

GOAL

Generate 3 practical, grounded QRA pairs that would help:
- Compliance assessors understanding the control
- Security engineers implementing the control
- Auditors verifying control effectiveness
- Risk analysts assessing control coverage

HARD RULES

1. Return 0 pairs if the control has no substantive description.
2. Do not invent implementation details, threats, or impacts not stated in the control.
3. Do not use outside knowledge.
4. The question must explicitly name the control ID (e.g., CWE-119).
5. The answer must be directly supported by quoted evidence from the control.
6. The reasoning may connect evidence but may not add new facts.
7. Prefer abstaining over guessing.

1. description

6. observed_examples (real-world CVEs)

- implementation_guidance (how to fix/prevent)
- assessment_criteria (how to test for)

REJECTION RULES

- the question can be answered with generic knowledge
- the answer contains any unsupported claim
- the question is too vague to be actionable

CONTROL RECORD
==============
Framework: CWE
Control ID: CWE-119
Title: Improper Restriction of Operations within the Bounds of a Memory Buffer

DESCRIPTION
-----------
The product performs operations on a memory buffer, but it reads from or writes to a memory location outside the buffer's intended boundary. This may result in read or write operations on unexpected memory locations that could be linked to other variables, data structures, or internal program data.

LIKELIHOOD OF EXPLOIT
---------------------
High

COMMON CONSEQUENCES
-------------------
1. Affects: Integrity, Confidentiality, Availability
   Impacts: Execute Unauthorized Code or Commands, Modify Memory
   Detail: If the memory accessible by the attacker can be effectively controlled, it may be possible to execute arbitrary code, as with a standard buffer overflow. If the attacker can overwrite a pointer's worth of memory (usually 32 or 64 bits), they can alter the intended control flow by redirecting a function pointer to their own malicious code.

2. Affects: Availability, Confidentiality
   Impacts: Read Memory, DoS: Crash, Exit, or Restart, DoS: Resource Consumption (CPU), DoS: Resource Consumption (Memory)
   Detail: Out of bounds memory access will very likely result in the corruption of relevant memory, and perhaps instructions, possibly leading to a crash. Other attacks leading to lack of availability are possible, including putting the program into an infinite loop.

3. Affects: Confidentiality
   Impacts: Read Memory
   Detail: In the case of an out-of-bounds read, the attacker may have access to sensitive information. If the sensitive information contains system details, such as the current buffer's position in memory, this knowledge can be used to craft further attacks, possibly with more severe consequences.

MODES OF INTRODUCTION
---------------------
- Phase: Implementation
  Note: Memory buffer operations are typically introduced during the coding phase.

POTENTIAL MITIGATIONS
---------------------
1. Phase: Requirements
   Strategy: Language Selection
   Action: Use a language that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid. For example, many languages that perform their own memory management, such as Java and Perl, are not subject to buffer overflows. Other languages, such as Ada and C#, typically provide overflow protection, but the protection can be disabled by the programmer.

2. Phase: Architecture and Design
   Strategy: Libraries or Frameworks
   Action: Use a vetted library or framework that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid. Examples include the Safe C String Library (SafeStr) by Messier and Viega.

3. Phase: Operation, Build and Compilation
   Strategy: Environment Hardening
   Action: Use automatic buffer overflow detection mechanisms that are offered by certain compilers or compiler extensions. Examples include: the Microsoft Visual Studio /GS flag, Fedora/Red Hat FORTIFY_SOURCE GCC flag, StackGuard, and ProPolice.
